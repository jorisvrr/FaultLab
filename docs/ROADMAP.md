# Checkpoint Roadmap

Each checkpoint ends with passing tests, updated docs, and an ADR for every significant decision. A checkpoint is *done* when its acceptance criteria are demonstrably met, not when its code exists. Order matters: each one relies on guarantees proven by the previous ones.

## CP0 — Deterministic core ✅

Three independently modelled nodes · virtual clock · deterministic priority queue · seeded PRNG · messages delivered at scheduled virtual times · reproducible trace · defined ordering of simultaneous events · `maxEvents` · unit + property tests · identical traces for identical inputs · determinism documentation.

## CP1 — Node lifecycle: crash and recovery

- Node status `running → crashed → recovering → running`; crash and recover as **scheduled fault events** (`FaultPlan` is data, recorded in `run.start`).
- **Volatile vs. persistent storage.** `ctx.storage.get/put` (JSON values). Writes are durable when the handler commits (atomic with the step). Crash discards volatile state, pending timers, and buffered effects. Recovery calls `init` (or a new `onRecover`) with persistent storage intact.
- **Incarnation numbers** on nodes. Timers from an old incarnation can never fire ([B7](FAILURE_MODES.md)).
- Messages to a crashed node: traced `message.drop { reason: 'node-down' }`.
- **Acceptance:** property tests: a crashed node handles no events; persistent writes survive crashes and volatile state doesn't; crash at an arbitrary time yields identical traces across runs; no timer fires across incarnations.

## CP2 — Network faults

- Per-link latency overrides; loss probability; duplication; scheduled partitions and heals (sets of node groups); optional FIFO links.
- `RoutingDecision` gains `drop` (with reason) and `duplicate`.
- **Acceptance:** partition semantics are symmetric and total (no message crosses a partition); loss rate converges statistically for a fixed seed; fault plans are validated at the boundary; random fault plans generated by fast-check still give reproducible traces.

## CP3 — Invariant checking

- `Invariant = { name, check(view) → ok | violation(detail) }`, evaluated after every step over a read-only global view (all node states, in-flight messages, time).
- Violations are trace entries; the policy can be stop or continue.
- Bounded-liveness helpers (e.g. "a leader exists by t=…") are kept separate from safety invariants.
- **Acceptance:** a deliberately buggy fixture protocol is caught; checkers cannot mutate state (frozen views); the cost per step is measured and documented.

## CP4 — Snapshots, replay, time travel

- A snapshot captures **all** execution-relevant state: clock, scheduler heap *including* cancelled entries and `nextSeq`, PRNG states, node runtimes (status, state, storage, counters, timers), trace length.
- Time travel = restore the nearest snapshot ≤ target, then re-execute. Snapshot interval is adaptive.
- **Acceptance:** metamorphic property `run(N) ≡ restore(snap@k) + run(N−k)` for random k and random experiments; snapshots serialise to JSON and round-trip.

## CP5 — Raft leader election

- RequestVote/AppendEntries heartbeats; randomized election timeouts from `ctx.random`.
- Invariants: **Election Safety** (≤ 1 leader per term); terms monotonic per node; a node votes at most once per term (persistent state).
- Test thousands of seeds with random crash and partition plans. When fast-check finds a failure, shrink it to a minimal fault plan.
- **Acceptance:** zero safety violations across ≥ 10 000 randomized experiments; a known-bad variant (e.g. a vote not persisted) is caught and shrunk.

## CP6 — Worker boundary and minimal UI shell

- `apps/web`: React + Vite. Simulation in a Web Worker; versioned, validated message protocol; trace streamed in chunks; wall-clock watchdog for runaway handlers.
- Unstyled but complete: configure, run, step, scrub, trace table, node state inspector.
- Playwright: smoke tests and **cross-browser determinism** (identical golden fingerprint in Chromium, Firefox, WebKit).
- ESLint + typescript-eslint introduced with the app.

## CP7 — Visual system and network visualisation

Applies [DESIGN_DIRECTION.md](DESIGN_DIRECTION.md) phases V0–V3: tokens, primitives, graph renderer prototype (measured), timeline and space-time diagram, causal highlighting.

## CP8 — Experiments: save, load, share

- IndexedDB persistence; JSON export/import validated at the boundary; share links encode *inputs* (compressed), never traces.
- Version compatibility: on load, re-run and compare the fingerprint; on mismatch, warn about engine/protocol drift.

## CP9 — Raft log replication and safety

Log Matching, Leader Completeness and State Machine Safety invariants; a client workload generator; optionally a linearizability checker for a replicated key-value store.

## CP10 — Performance engineering

Profile before optimising. Targets: 100+ nodes, 10⁶+ events. Candidates: heap compaction, trace chunking/diff encoding, render LOD, typed-array event storage. Rust/WASM only if profiling shows the engine (not rendering) is the bottleneck and a prototype proves the gain ([ADR-0001](adr/0001-repository-layout.md) keeps that door open).

## CP11 — User-defined protocols

A separate security architecture ADR first: isolation (Worker + SES/ShadowRealm, or a QuickJS-in-WASM interpreter with deterministic fuel metering), resource limits, API surface, threat model. Never remote execution.

## Next engineering challenge (CP1)

The hard part of CP1 is not the crash itself but **defining what survives it**, so that "crash" is a meaningful model of a real machine:

1. **Durability boundary.** Persistent writes become durable when the step commits. That models an `fsync` at the end of each handler. Is that too generous? Real Raft bugs come from writes that were *not* durable. CP1 should allow (and test) a later "lose un-synced writes" mode.
2. **Incarnations.** Every timer and every node gets an incarnation number, so a pre-crash timer can provably never fire into a post-recovery node.
3. **Fault events are inputs.** Crashes must be scheduled events in the same total order as everything else, recorded in `run.start`. Otherwise the experiment is not reproducible.
